Workout Tracker

I tracked my lifts in a Google Sheet that only ever held the latest numbers. Every session overwrote the one before it, so there was nothing to look back at and no progression to see. This is the app that replaced it, and this is how it was built.

Try the demo Source on GitHub

The demo needs no account. It runs the real logger on a made-up lifter’s data, so you can start a workout, log sets, watch the targets adjust and feel the rest timer. Nothing you do there is saved anywhere.

The problem with the spreadsheet

A spreadsheet is a good enough place to write down what you lifted. It is a bad place to keep it. Mine held one row per exercise with the most recent weight and reps, which meant every session destroyed the evidence of the one before it. I could tell you what I lifted last Tuesday. I could not tell you whether it was more than in June.

Three things followed from that. There was no progression to chart, because there was no history to chart it from. It was unpleasant to use on a phone between sets, which is the only moment it actually gets used. And there was nothing useful to point an analysis at later, because the data had been overwritten rather than accumulated.

There was a fourth problem that was mine rather than the spreadsheet’s: I kept skipping warm-ups. Not out of principle, just because working out what to warm up with is arithmetic you do not want to do while standing at a rack.

One rule: no thinking at the rack

Everything in the app comes back to a single design rule. You are using it standing up, mid-set, with about twenty seconds of attention and a heart rate that makes arithmetic unappealing. So the app never asks you a question it could answer itself. It tells you the next thing to do.

That rule is why a working set arrives pre-filled with a weight and a rep count rather than an empty box, why the rest timer starts itself, and why the warm-up is calculated instead of left to you. A field you have to think about is a field you eventually stop filling in, and a log with gaps in it is worth less than no log at all.

It also set four rules the build was not allowed to break, written into the spec before any code existed:

  • Sets are append-only, permanently Logged history is never overwritten or deleted. This is enforced in the database rather than trusted to the app: there is no delete policy on the table, and a trigger rejects any update except setting a soft-delete timestamp once.
  • Nothing derived is ever stored Estimated one-rep max, volume and personal bests are computed in SQL views from the raw sets. A stored total is a number that can silently disagree with the rows it came from.
  • Weights are stored in kg, converted only for display One unit in the database, one conversion at the edge.
  • Logging a working set takes one tap The 390px phone screen is the design target, not a fallback.

What a workout actually looks like

It picks the day for you. The app knows which day of your plan comes next from what you last trained, so opening it on a training day takes one tap to start. Plans come from templates (Full Body, Upper Lower, Push Pull Legs, Bro Split), recommended by how many days a week you train, and every one of them is editable down to the individual exercise. New accounts get a short setup that adapts the plan to a gym, a pair of dumbbells at home, or nothing but bodyweight.

The warm-up is worked out, not remembered. A checklist is built from the muscles that day actually trains: cardio matched to the session, then a drill for each muscle area, each one labelled with the exercises it is preparing you for. Then the first exercise of the day gets ramp-up sets at 50% for 10 reps and 75% for 5, taken from the weight you are aiming for today and rounded to 2.5 kg, because 2.5 kg is the plate you actually have. Later exercises skip the ramp, since you are already warm. The workout ends the same way: a cool-down checklist of stretches for whatever you worked hardest.

Every set arrives filled in. A working set shows the weight and reps you are aiming for, with last session printed underneath for reference: Last time: 80 kg × 6, 6, 6, 6. Logging it is one tap. Change the weight on set one and the later sets follow it. Reps have a minus and plus pill so one rep more is a tap rather than a keyboard.

Then it asks how that felt. Four chips: Easy, Good, Hard, Max. That one answer is what makes the next set adapt, and the next session adapt after it. It is optional, and skipping it is read as Good.

The rest timer starts itself the moment you tick a set, and it beeps: one short tone when the rest begins, two higher ones when it is over, alongside a vibration. The tones are generated in the browser rather than loaded as files, so there is nothing to download or cache. A speaker button mutes them if you would rather it stayed quiet.

Machines get the weights machines actually have. A stack gives you 2.5 kg steps, but most machines also have a small add-on weight sitting on the pin, 1.25 kg or thereabouts. The app records that separately, so a set reads 22.5 + 3.75 kg rather than being rounded to whatever the stack alone could do. It sounds like a detail. It is the difference between the app describing your actual training and describing an approximation of it.

The analysis, and how it runs without API credits

This is the part I am happiest with, and it started as a cost problem. I wanted every finished workout analysed against the last one: what moved, what stalled, what to watch. The obvious way to do that is to call an AI API from the server and pay per workout. For an app with one user that is a subscription to run a feature I use four times a week.

So it does not call an API at all. Instead the database talks to my own Claude account directly, through a routine I have already got.

Finishing a workout stamps it as ended. A Supabase database webhook fires on that one column changing and calls an Edge Function, which triggers a Claude routine on my account. Claude reads the workout straight out of the database, compares it against previous sessions of the same exercises, and writes a review row back. The app polls for it and shows it on the workout’s page.

The interesting work is in what the Edge Function refuses to do. It fires only when a workout goes from unfinished to finished, and only for workouts logged in the app: cancelling one, importing old data from the spreadsheet, or editing something afterwards all look like updates to that table, and none of them should cost an analysis. It authenticates the caller with a shared secret compared in constant time, so a wrong guess does not leak how wrong it was. The secret and the routine’s address live only in Supabase, never in the repository, and the function logs the workout id and the response status without ever logging the token or what came back.

The database side has its own guard. The obvious permission for the insights table lets you mark your own review as read, but written the obvious way it also lets you rewrite the text of the review itself. Permission was narrowed to that one column, so the app can mark something read and cannot edit what Claude said about your training.

Seeing the progress

This was the entire point of leaving the spreadsheet, so it gets real treatment rather than a number on a card. Every exercise has a chart of estimated one-rep max per session, its best set, and a table of the sessions behind the line. The Progress tab shows how consistent you have been: a streak counted in weeks rather than days, because a daily streak is the wrong shape for lifting and punishes rest days, a twelve-week calendar, and sets per muscle this week against last week so you can see what you have been quietly neglecting.

All of it is computed from the raw sets at the moment you look, through database views that exclude warm-ups, deleted sets and cancelled workouts. The chart draws straight segments between sessions rather than a smooth curve, which sounds like a styling choice and is not: a curve implies you had a value on the days in between, and you did not.

The gym basement problem

Gyms have bad signal, and an app that loses a set because a wall got in the way is an app you stop trusting. Every change the logger makes goes into a queue on the phone before it is sent anywhere. The screen updates immediately and never un-ticks itself because a request failed.

Getting that right is mostly about being safe to repeat. Each set carries an id generated on the phone, so if a request is sent twice the second one is recognised as the same set rather than logged again. Updates only apply to rows still in the state they expect. The queue is sent oldest first and stops on the first transient failure, so an answer about how a set felt can never overtake the set itself. You can finish a workout with no signal at all: it saves on the phone, and syncs, and the analysis starts when it lands.

How it was built

Next.js on Vercel, Supabase for the database and authentication, and Claude Code writing the code. I wrote the build spec first: what the app is, the data model, the screens, and the numbered rules above. Then it went milestone by milestone, with a plan approved before each one.

The honest description of my role is that I did not type the code, and I decided what it should do. The repository keeps an append-only decision log, and 20 of its 31 entries record a change I asked for and the reasoning behind it: only the first exercise ramps up, warm-ups round to 2.5 kg, sets start at the aim rather than last session, one exercise open at a time, the rest timer beeps, the add-on weight, the cool-down, the demo instead of a login wall. The spec said the app should work offline and compute rather than store; the texture of actually using it came from using it.

That log is also the part I would point a sceptical reader at. It records what changed and why, including the things that were wrong the first time, which is a more useful account of a build than a commit history.

What keeps it honest

This is a personal app holding training history that cannot be reconstructed if it is lost, so the checks are heavier than the size of it suggests: 112 unit tests across the progression rules, warm-up and cool-down logic, rotation, unit conversion, the offline queue and the spreadsheet import, plus 76 database assertions that run against a real PostgreSQL instance on every push and prove that row-level security actually isolates users and that the append-only guarantee holds.

The deploy order matters as much as the tests. Lint, typecheck, unit tests, build and the database checks run first; then migrations are applied; then the app deploys. Getting that sequence backwards was a real bug, not a hypothetical one: the app shipped ahead of its own schema and briefly told me the database needed an update. Vercel’s own Git deploys are switched off, so nothing reaches production without passing through that pipeline.

What broke

A view that would have leaked every user’s data. The schema exposes working sets through a database view. A plain view executes as whoever owns it, not as whoever queries it, which would have quietly bypassed row-level security and returned every account’s sets to anyone who asked. It was caught reviewing the migration before it was applied. It is the kind of bug that would never surface in testing, because with one account in the database the wrong answer and the right answer are identical.

Every request on the live site returning a 500. The two Supabase configuration values were set as Secret type in Vercel. Pulling the environment during a build returns Secret values as the literal text [SENSITIVE], so the built app was trying to reach a server at the address “[SENSITIVE]” and failing on every request. The deploy now reads those two public values from a known source and refuses to deploy at all if the address is not a valid one.

A green pipeline that was lying. A step piped its output through tee to print it, and in a shell without pipefail that hands back the exit code of tee rather than the command that failed. A failed database seed reported success.

A sync lock that locked permanently. When the outbox tried to send with no connection, the run finished immediately, and the lock was cleared before it had been set, which left it stuck on and blocked every sync after it. Found in testing rather than in a gym.

Where it is now

Live, and it is what I train with. Plans, the logger, warm-ups and cool-downs, progression, the rest timer, History, Progress charts, offline logging and the post-workout analysis are all working. It installs to a phone home screen. You can try the whole logger in the demo without an account.

Still to come, named rather than implied: starting a workout with no signal at all (a dropout mid-workout is handled, opening the app cold in a basement is not), offline History and Progress, and editing warm-up templates per exercise. The analysis currently reviews one workout against previous ones; weekly and plateau reviews are in the schema and not yet written.

Workout Tracker

I tracked my lifts in a Google Sheet that only ever held the latest numbers. Every session overwrote the one before it, so there was nothing to look back at and no progression to see. This is the app that replaced it.

Open the app Source on GitHub

It stores personal training history, so it opens on a sign-in screen. The repository is public if you would rather read how it works than sign up: the build spec, the decision log, the tests and the CI configuration are all in there.

Problem

A spreadsheet is a good enough place to write down what you lifted. It is a bad place to keep it. Mine held one row per exercise with the most recent weight and reps, which meant every session destroyed the evidence of the one before it. I could tell you what I lifted last Tuesday. I could not tell you whether it was more than in June.

Three things followed from that. There was no progression to chart, because there was no history to chart it from. It was unpleasant to use on a phone between sets, which is the only moment it actually gets used. And there was nothing useful to point an analysis at later, because the data had been overwritten rather than accumulated.

Approach

I wrote the build spec before any code existed: what the app is, the data model, the screens, and a numbered list of rules the build was not allowed to break. Then I built it milestone by milestone with Claude Code, approving a plan before each one. The spec and the decision log are both in the repository, and the decision log is where the interesting part lives, because it records every place the plan changed and why.

Four of those rules did most of the work:

  • Sets are append-only, permanently Logged history is never overwritten or deleted. This is enforced in the database rather than trusted to the app: there is no delete policy on the table, and a trigger rejects any update except setting a soft-delete timestamp once.
  • Nothing derived is ever stored Estimated one-rep max, volume and personal bests are computed in SQL views from the raw sets. A stored total is a number that can silently disagree with the rows it came from.
  • Weights are stored in kg, converted only for display One unit in the database, one conversion at the edge.
  • Logging a working set takes one tap The 390px phone screen is the design target, not a fallback, and every value is pre-filled from the same set last session, so confirming it is the whole interaction.

The last one is the product decision the rest hangs off. The app is used standing up, mid-set, with about twenty seconds of attention. Anything that takes longer than that does not get logged, and an exercise log with gaps in it is worth less than no log at all.

What keeps it honest

This is a single-user app holding years of training history that cannot be reconstructed if it is lost. That makes correctness worth more than features, so the checks are heavier than the size of the thing suggests: 71 unit tests covering the progression rules, the warm-up logic, the rotation, the unit conversion and the spreadsheet import, plus 38 database assertions that run against a real PostgreSQL 16 instance on every push and prove row-level security actually isolates users and that the append-only guarantee holds.

The deploy order matters as much as the tests. Lint, typecheck, unit tests, build and the database checks all run first; then migrations are applied; then the app deploys. Getting that sequence backwards was a real bug, not a hypothetical one: the app shipped ahead of its own schema and briefly told me the database needed an update. Vercel’s own Git deploys are switched off, so nothing reaches production without going through that pipeline.

What broke

A view that would have leaked every user’s data. The schema exposes working sets through a database view. A plain view executes as whoever owns it, not as whoever queries it, which would have quietly bypassed row-level security and returned every account’s sets to anyone who asked. It was caught reviewing the migration before it was applied, and the view is created with caller-level security instead. It is the kind of bug that would never have shown up in testing, because with one account in the database the wrong answer and the right answer are identical.

Every request on the live site returning a 500. The two Supabase configuration values were set as Secret type in Vercel. Pulling the environment during a build returns Secret values as the literal text [SENSITIVE], so the built app was trying to reach a server at the address “[SENSITIVE]” and failing on every single request. The fix was to stop trusting the pull: the deploy now reads those two public values from a known source and refuses to deploy at all if the address is not a valid one.

A green pipeline that was lying. A step piped its output through tee to print it, and in a shell without pipefail that hands back the exit code of tee rather than the command that failed. A failed database seed reported success. Found while reviewing the workflow rather than by anything going wrong, which is the only reason it is in this list instead of a much worse story.

Where it is now

Live and in use for my own training. You can build a plan from a template (Full Body, Upper Lower, Push Pull Legs or Bro Split, recommended by how many days a week you train), edit it down to the individual exercise, and log against it: a warm-up checklist built from the muscles that day trains, ramp-up sets on the first exercise, working sets pre-filled from last time, a rest timer that starts itself, and personal bests computed as you go. It installs to a phone home screen as a PWA.

Not built yet, and named here rather than implied: the History and Progress screens are still placeholders, so the progression logic runs but you cannot yet chart it. Offline logging is specified and not started. The AI analysis is the reason the data model looks the way it does, and it is the next thing worth building, but there is no AI in the app today and I would rather say so than let a tech list imply otherwise.

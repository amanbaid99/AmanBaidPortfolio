Second Brain

Every AI chat starts by forgetting who I am, and throws away everything I tell it when the window closes. I built a Notion workspace that holds that context permanently, with a retrieval protocol that tells the assistant how little to read, and a start prompt that works in any tool.

This is my own workspace and it holds personal records, so there is no link and no screenshots. Everything below is structure and mechanics. The example prompts are real, with page links and database identifiers removed, and any content shown is invented.

Problem

Three things go wrong when you use an AI assistant seriously over months rather than minutes.

Every chat has a finite context window. A long conversation starts to drift. The model contradicts something I told it an hour earlier, or fills a gap with something plausible that I never said. The longer and more useful the conversation gets, the less reliable it becomes.

Context is locked inside one platform. Whatever an assistant learns about me belongs to that vendor. Moving from one tool to another means re-explaining my work, my projects and my priorities from scratch. The memory is not mine in any practical sense.

The obvious workaround makes it worse. Keeping one long document about yourself and pasting it in means paying for the whole document on every question. Ask something that needs two lines of it and the model still reads all of it, badly, and you have spent most of the window before the actual question starts.

Why the existing options fall short

Built-in memory features are per-vendor and mostly opaque. I cannot see the whole of what has been remembered, cannot correct a specific wrong belief, and cannot take it anywhere.

One long context document is portable and inspectable, which is better, but it has no structure an assistant can navigate. Every question costs the whole document.

Vector search over personal notes is the right answer at scale. On a corpus this small it is heavy to run and the retrieval is fuzzy: you get three near-identical chunks and no sense of which is current.

Notion search on its own finds pages but does not know when to stop reading. Search is not a protocol.

None of them answers the question that actually matters, which is not where is the information but how much should I read to answer this.

The insight

Treat context like a well-indexed database, not a long document. The assistant should navigate to what it needs instead of reading everything.

An assistant that reads one directory page, then one summary, then one section gives a better answer than one that skims forty pages, and it spends a fraction of the window doing it. That reframing is the whole project. The rest is the structure that makes navigation possible and the rules that make it happen.

Architecture

Five top-level containers, borrowed from the usual note-taking split, plus three pages that exist only for the assistant. 

Second Brain
├── Index            the directory: snapshot, map table, change log
├── Guide for AI     the rules, including the retrieval protocol
├── Chat Prompts     prompts that bind one chat to one page
│
├── Inbox            quick capture from my phone, unprocessed
├── Areas            ongoing, no finish line
│   └── Area page        Summary / Current status / Log
│       └── sub-page     anything long lives here, listed in the Summary
├── Projects         things with a finish line
├── Resources        reference and learning
├── Archive          inactive
└── Tasks            database: status, due date, area, project relation

Every section page has the same three blocks, in the same order:

  • Summary What is on this page, which sub-pages exist, and the date it was last updated. Always at the top.
  • Current status Short, and always describes today. Not a history.
  • Log Dated entries, newest first, one line each. The history lives here so Current status never has to carry it.

The Summary is the load-bearing block. It is not a description for a human, it is a routing table for the assistant: it says whether the answer is on this page, one level further down, or not here at all. Without it, every question costs a full page read, and the structure stops earning its keep.

How retrieval works

The Guide for AI page holds a numbered protocol. Any assistant reads it before answering anything about me. 

A question arrives
        │
        ▼
Read the Index                    one page: a snapshot, plus a map of
        │                         every section and where it lives
        ▼
Pick only the sections it names   ignore the rest of the workspace
        │
        ▼
Read that page's Summary          what is here, what is below
        │
        ├──── answer is here ──────────────►  answer, stop
        │
        ▼
Open Current status, the Log, or a named sub-page
        │
        ▼
Answer, stop

The rule that does the work is the negative one at the end of the protocol: never read the whole workspace to answer one question. Without it a capable model will helpfully read everything, which is the behaviour the whole system exists to prevent.

Writing follows the same path in reverse. When I share an update, the assistant finds the right page through the Index, updates Current status, adds a dated Log line, refreshes that page's Summary, and only touches the Index if the change matters at the top level. Then it confirms in one line what it changed. The confirmation is not politeness: it is how I catch a wrong write immediately instead of three weeks later.

Workflow: one main chat, many page chats

The main chat owns the structure. It creates, moves and deletes pages, keeps the Index and the Summaries in step, and writes the prompts for every other chat. It is the only chat allowed to change the shape of the workspace.

Page chats each own exactly one page. A chat for tasks, a chat for applications, a check-in chat for a journal-style page. Each one reads its page at the start of a conversation, writes back what I tell it, and is explicitly forbidden from touching anything else. If something belongs elsewhere, the rule is to say so rather than guess.

The scope limit is the point. A chat that can only see one page cannot drift into an unrelated part of my life, cannot quietly restructure anything, and starts every conversation grounded in current data rather than in whatever it inferred twenty messages ago. Conversations stay short because the surface is small, and everything said in them ends up back in Notion instead of dying with the tab.

Portability comes from a universal start prompt. Any assistant with access to the workspace loads the same context the same way. The memory lives in the data, not in the vendor. Switching tools costs one paste.

Two integrations hang off the same rules. A task with a due date also becomes a calendar event with a reminder, so the list and the calendar cannot disagree. Outreach is written into my mail client as a draft and never sent: the draft is the handoff point, and anything that would leave in my name gets a human check first.

Example prompts

Two of the real prompts, with page links and database identifiers removed and the field values replaced with invented ones. First, a page chat. Note how much of it is restriction rather than instruction. 

You are my Tasks chat. You manage one Notion database only, my Tasks list.

Fields: Task name, Status (Not started / In progress / Done / Archived),
Due (date), Area (Work, Finance, Health, Personal), Project (relation to
my project list).

At the start of every conversation, query the database for open tasks,
so you know what is pending.

What you do:
- When I dump to-dos, messy is fine, turn each into a short action-first
  task name. Set Area and Project if obvious. Set Due only if I give a
  date or a deadline. Status starts as Not started.
- If the area, project or due date is unclear, add the task anyway, then
  ask in one short line.
- Any task with a due date also goes on my calendar as a 10:00 event with
  a reminder. If the date changes, or the task is done or dropped, update
  the event to match.
- "Done X" marks it Done. "Start X" marks it In progress. "Drop X" marks
  it Archived. Never delete tasks.
- When I ask what is on my plate, list open tasks grouped as Overdue,
  Today, This week, Later, No date. Short lines only.
- After changes, confirm in one line per task.

Rules:
- Only touch the Tasks database and my calendar. Never edit other pages.
  If something belongs elsewhere, tell me to take it to my main chat.
- No em dashes anywhere. Use commas, colons or hyphens.

Second, the universal start prompt. This is the portability layer, and it is eight lines long because the workspace carries the rest. 

You have access to my Notion. My "Second Brain" is the source of truth
about my life and work.

Before answering anything about me:
1. Read the "Guide for AI" page and follow its rules.
2. Read the "Index" page, which is the directory.
3. Open only the sections the Index points to, reading each page's
   Summary block first. Go deeper only if needed.

When I share updates, write them to the right page as the Guide
describes. If you cannot write to Notion, tell me exactly what to change
and where.
No em dashes anywhere.

Results

I use this every day, and four things changed.

Conversations got short. A page chat reads a summary and one page instead of being told the story again. I stopped opening a chat with two paragraphs of background.

Drift dropped. Not because the models got better but because each chat has one job and one page. A chat that can only see a task list has nothing to invent about anything else.

Switching tools stopped costing anything. The same eight-line prompt loads the same context anywhere with access to the workspace.

The memory became inspectable. When an assistant is wrong about me now, I can open the page and see exactly why, and fix the page rather than argue with the model. That is the difference between memory I own and memory a vendor keeps for me, and it is the part I did not expect to value most.

I have not measured any of this. There is no token count, no before and after, no controlled comparison. It is a working system I rely on, not an experiment with numbers, and I would rather say that than put a figure here I cannot stand behind.

Limitations

  • Inbox processing is manual Capture from my phone is instant, but filing is not. I have to open a chat and ask for the inbox to be processed. Nothing happens on its own.
  • Summaries can go stale Page chats edit pages the main chat is not watching. The Guide tells the main chat to re-read a Summary before relying on it, but that is a convention I wrote, not something the system enforces.
  • The protocol is advisory It works because the assistant chooses to follow it. A model that skips the Guide reads too much or too little, and nothing stops it. The rules are a prompt, not a permission system.
  • One workspace, one dependency If access to Notion breaks, the memory is unreachable. There is no local copy and no export routine.
  • The trade is deliberate This only works because personal context is written somewhere an assistant can read it. I decide what goes in, and some things do not.

What is next

A scheduled weekly review. Something that reads the Logs on a timer and writes a digest, so the system tells me what changed instead of waiting to be asked. This is the biggest gap: right now the workspace is entirely passive.

Automatic inbox processing. A trigger on new capture rather than me remembering to file.

A staleness check. Flag any page whose Summary is older than the newest line in its own Log. That is a rule a script can enforce, which moves it out of the advisory category.

Actually measuring it. Context consumed per answer, with and without the protocol, on the same set of questions. If the central claim is that navigation beats reading everything, it should be possible to show it.

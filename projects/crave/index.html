Crave

One natural-language box in front of three different ordering surfaces. You describe what you want in plain English — Crave works out whether that’s a food delivery, a grocery run or a table booking, pulls out the details, and assembles the order.

Open the live demo View the code

No sign-in and no API key — click one of the example requests and watch it route.

Problem

Most ordering apps make you know where you’re going before you start. You have to decide it’s a delivery order, or a grocery order, or a reservation, and open the right app first — even though the thing in your head was never sorted that way. “I want to make mac and cheese, order all the ingredients” is one intention that happens to land in a grocery basket; “team dinner for 8 near Koramangala” is one intention that happens to land in a booking.

Crave inverts that: you describe what you want, and working out the destination is the software’s job.

Approach

Because the routing decision is the product, I made the interface show it rather than hide it. The three surfaces sit side by side, a scan runs across them while the request is in flight, and the chosen one locks in. A spinner would have been easier and would have concealed the only thing worth watching.

Two decisions then shaped the architecture. First, the found / substituted / not-found pattern is a single reusable component rather than three per-flow implementations, so an out-of-stock swap reads identically everywhere it appears. Second, Crave assembles carts but never takes a payment — every flow ends in a handoff to the platform’s own checkout. The service interface deliberately exposes no order-placement tool and touches no payment instrument, which makes “nothing happens without you” a property of the architecture rather than a policy the code chooses to honour.

What I built

  • Three complete workflows behind one box. A preference reorder recalls your saved usual and asks — never assumes — whether to save any edits. A recipe request decomposes a dish into an ingredient list and checks each item against a catalog, resolving what’s in stock, what needs substituting and what simply isn’t available. A group request ranks venues against a per-head budget with bookable time slots.
  • One reusable resolution component for found / substituted / not-found, shared across all three flows instead of reimplemented per flow.
  • Zero-configuration intent routing. Two interchangeable engines sit behind one typed contract: Claude with structured outputs when an API key is present, a local rule-based router when it isn’t. Nothing to set up before you can try it.
  • One source tree, two builds. The same code produces a server build and a fully static export, the latter deployed automatically to GitHub Pages — which is what makes the public demo runnable with no key.

What it demonstrates

  • A prototype built to show the working, not the workings The point is that you can type a sentence and watch it resolve into the right order. It is a working prototype, not a shipped product with real merchants behind it — so there are no adoption or conversion numbers here to claim.
  • Routing made legible instead of magical Showing the surfaces being scanned turns the one interesting decision into something a person can see, judge and disagree with.
  • “It can’t buy anything” is enforced by the architecture There is no order-placement tool and no payment instrument in the system at all, so the safety property doesn’t depend on the model behaving.
  • The same product works with and without an LLM Putting both engines behind one typed contract keeps the model a swappable implementation detail rather than a hard dependency.
